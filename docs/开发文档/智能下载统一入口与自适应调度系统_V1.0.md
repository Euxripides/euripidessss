# 智能下载统一入口与调度系统 V1.0
## Smart Download Hub + Adaptive Orchestrator

> 目标：用一个新的“智能下载”入口统一现有浏览器/CSV、直链、网页采集、SQD、RPC、SQD Cloud 等下载能力。  
> 用户只负责“地址 + 链 + 数据类型 + 可选时间范围”，系统负责探测数据量、自动选路、并行执行、失败切换、断点续传、完整性校验、结果标准化与前端展示。  
> 本设计重点解决当前前端下载入口分散、调度逻辑不透明、任务进度不可控、不同 Provider 切换后数据格式不兼容的问题。

---

# 1. 核心原则

1. **前端只有一个主入口：智能下载**
   - 原“Parquet 数据 / 浏览器下载 / Dune 下载 / 其他下载入口”逐步降级为高级工具，不再作为普通用户主入口。
   - 用户不需要理解 Provider，也不需要配置 API Key。
   - 系统自动调用系统设置中已经保存并通过健康检查的 Provider/API。

2. **地址是一级任务，数据类型是二级子任务**
   - 每个地址都必须拥有独立任务、独立状态、独立进度条、独立暂停/继续/取消能力。
   - 一个地址下可同时包含：交易、内部交易、代币转账、NFT、日志、余额、Token Metadata 等多个 Dataset 子任务。
   - 一个批量任务可以包含 1～100,000 个地址，但 UI 必须始终能够定位到单个地址的真实进度。

3. **下载方式不是任务身份**
   - 同一个任务可从 CSV 切换到 SQD、RPC、SQD Cloud。
   - Provider 只是“执行通道”，不能绑定任务数据模型。
   - 切换 Provider 后继续使用同一个 Task / Dataset / Checkpoint，不重建逻辑任务。

4. **先探测，后下载**
   - 系统先快速估算每个地址、每个数据类型的规模，再决定 Provider。
   - 小数据优先使用成本低、速度快的 CSV/API/直链。
   - 中大数据使用 SQD / RPC / 批量数据源。
   - **只有其他下载方式全部不可用或连续失败，才启用 SQD Cloud 最终兜底。**

5. **完整性优先于速度**
   - “下载成功”不等于“任务完成”。
   - 必须经过结构校验、唯一键校验、时间/区块覆盖校验、数量核验、缺口扫描、必要时交叉 Provider 复核后才进入 `COMPLETED`。

6. **所有 Provider 原始数据最终统一为 Canonical Schema**
   - Provider 切换不影响下游。
   - 前端表格、DuckDB、资金流图、智能调查等全部读取统一结果层。

# 9. 智能调度器

## 9.1 任务层级

```text
BatchJob
└── AddressJob
    ├── DatasetJob: transactions
    ├── DatasetJob: internal_transactions
    ├── DatasetJob: token_transfers
    ├── DatasetJob: logs
    ├── DatasetJob: balances
    └── DatasetJob: metadata
```

**调度的最小单位建议为 `Address + Dataset + Range`，而不是整个地址。**

原因：

同一个地址可能：

- Transactions 很小 → CSV
- Logs 很大 → SQD
- Internal Transactions → RPC/Trace Provider
- Balance → RPC
- Metadata → API

因此一个地址内部可以并行走不同下载方式。

```go
}
```

# 12. 数据量分级

初始建议阈值，可在运行数据积累后动态学习。

## S：小地址 / 小 Dataset

```text
预计记录 <= 10,000
或预计数据 <= 20 MB
```

优先：

1. CSV / 官方页面接口
2. 直链下载
3. RPC
4. SQD

特点：

- 启动快
- 不值得创建大型 SQD Job

---

## M：中等规模

```text
10,000 < 预计记录 <= 500,000
```

优先：

1. SQD
2. 批量 API / 直链
3. RPC
4. SQD Cloud

---

## L：大地址

```text
500,000 < 预计记录 <= 5,000,000
```

优先：

1. SQD
2. AWS / bulk dataset（支持该 Dataset 时）
3. RPC 分块补洞
4. SQD Cloud

---

## XL：超大地址

```text
> 5,000,000 records
```

默认：

1. 提示该地址数据量巨大，但仍自动执行；
2. 优先 SQD / Bulk；
3. 强制使用 Range Partition；
4. 自动切分：
   - 时间窗口
   - Block Window
   - Dataset Partition
5. 多 Provider 并行；
6. SQD Cloud 最终兜底。

# 13. “SQD Cloud 最后使用”规则

只有满足以下条件之一才能进入：

```text
FALLBACK_SQD_CLOUD
```

- 所有本地/普通 Provider 对该 Dataset 均不支持；
- 所有可用 Provider 健康分低于最低阈值；
- 同一 Range 连续切换 >= N 个 Provider 后仍失败；
- Provider 返回确定性“数据不可获得”；
- Validator 确认存在缺口，且其他 Provider 无法补齐；
- 用户任务已超出 RPC / CSV 合理规模。

不能因为一次 503 就直接进入 SQD Cloud。

# 14. Provider 并行策略

“不同下载方式可以并行”应分两类。

## 14.1 不同 Dataset 并行

例如：

```text
Transactions → CSV
Token Transfer → SQD
Internal Tx → RPC
Balance → RPC
```

可同时运行。

## 14.2 同 Dataset 分区并行

例如超大地址：

```text
2024 H1 → SQD
2024 H2 → SQD
2025 H1 → Direct/Bulk
2025 H2 → SQD
缺口区间 → RPC
```

但必须保证：

- Range 不重叠，或允许重叠但统一去重；
- 每个 Range 独立 checkpoint；
- 最终 Merge 后进行全局唯一键校验。

# 15. 最重要：下载方式切换兼容性

这是本系统的核心。

## 15.1 禁止以 Provider Schema 作为结果 Schema

错误方式：

```text
CSV结果一套字段
SQD结果一套字段
RPC结果一套字段
```

这样 Provider 一切换，Checkpoint、Merge、Validator、前端都会失效。

正确方式：

```text
Provider Raw
   ↓
Provider Normalizer
   ↓
Canonical Record
   ↓
Staging Parquet
   ↓
Merge / Dedup / Validate
   ↓
Final Dataset
```

# 17. Universal Checkpoint V3

Checkpoint 不能只记录：

```text
provider_page = 56
```

因为换 Provider 后 page=56 没意义。

应该记录 Provider 无关的位置：

```json
{
  "task_id": "...",
  "address": "0x...",
  "dataset": "token_transfers",
  "requested_range": {
    "from_block": 40000000,
    "to_block": 50000000
  },
  "completed_ranges": [
    [40000000, 40999999],
    [41000000, 41999999]
  ],
  "active_range": [42000000, 42999999],
  "records_committed": 128883,
  "parts": [
    {
      "part": "part-000001.parquet",
      "sha256": "...",
      "rows": 25000
    }
  ]
}
```

Provider 私有状态单独放：

```json
{
  "provider_state": {
    "provider": "sqd",
    "cursor": "...",
    "page": null
  }
}
```

切换 Provider 时：

- 保留 `completed_ranges`
- 丢弃或归档旧 `provider_state`
- 新 Provider 从未完成 Range 继续

# 19. Provider 切换流程

```text
RUNNING
  ↓
Provider Error
  ↓
错误分类
  ├─ 短暂错误 → 原 Provider Retry
  ├─ 限流 → 降并发 + Retry
  ├─ 503 → 冷却 + Retry
  ├─ 能力不支持 → 立即切换
  ├─ 数据不完整 → Validator 标记缺口
  └─ 连续失败 → SWITCHING_PROVIDER
                     ↓
              选择次优 Provider
                     ↓
              从未完成 Range 继续
```

前端显示：

```text
SQD → RPC
原因：SQD 连续 503，60s 冷却
已完成：62.4%
无需重新下载已完成区间
```

# 25. ETA 计算

每个 Dataset 独立计算 ETA，再推导地址 ETA。

不要只使用：

```text
remaining_bytes / current_speed
```

使用 EWMA：

```text
smoothed_throughput =
  α * current_throughput
+ (1-α) * previous_throughput
```

考虑：

- 503 冷却
- Retry
- Provider 切换
- Validator 时间
- Processing 时间

前端显示：

```text
预计剩余：约 2 分 18 秒
置信度：高
```

切 Provider 后：

```text
预计时间重新计算中…
```

# 27. 下载完整性校验

建议建立 `Validation Pipeline V2`。

## Level 1：文件级

- 文件存在
- Parquet footer 可读
- Schema 正确
- SHA256
- 行数 > 0 或确认空集合法
- 临时文件全部关闭

## Level 2：记录级

- 唯一键
- 去重
- 地址格式
- block_number 合法
- transaction_hash 合法
- log_index / trace_address 合法
- 数据类型匹配

## Level 3：Range 覆盖

检查目标：

```text
requested range
=
valid completed ranges
+
confirmed empty ranges
```

不允许出现未知洞。

## Level 4：Provider Count 对账

Provider 能提供 total count 时：

```text
expected_count
vs
normalized_unique_count
```

例如：

```text
Expected: 1,281,442
Actual:   1,281,442
PASS
```

# 46. 文件 Part 规则

延续稳定的 Part 模型：

```text
part-000001.parquet
part-000002.parquet
...
```

要求：

- Part 编号单调递增
- SHA256 去重
- 已上传/已提交 Part 不重复写
- checkpoint 只指向已提交 Part
- Provider 切换后继续编号
- Provider 不能决定 Part 命名

这样可以彻底避免“换下载方式后重新编号、重复 Part、重复上传”等问题。

# 63. 可靠性验收

3. 自动切 SQD
4. 最终 100%
5. 不重复下载前 30%

3. Circuit Open

5. RPC 从未完成 Range 继续

3. 最终进入 SQD Cloud
4. SQD Cloud 只下载缺失区间

# 67. 建议的实施顺序

建议 Codex 按以下顺序实现，避免前后端再次失配：

```text
Step 1  定义 Canonical Schema
Step 2  定义 Task / Dataset / Range 数据模型
Step 3  Universal Checkpoint V3
Step 4  Range Ledger
Step 5  Provider Adapter 统一接口
Step 6  Discovery / Size Estimator
Step 7  Smart Scheduler
Step 8  Provider Switching
Step 9  Validation Pipeline
Step 10 Progress Aggregator + ETA
Step 11 REST + SSE
Step 12 新智能下载前端
Step 13 Result Processor + Result Table
Step 14 Dataset Registry 复用
Step 15 真实链容灾压力测试
```

**不要先重写下载器。**

本次工作本质上是：

> 在已有下载器之上增加统一任务模型、统一 Schema、统一 Checkpoint、智能调度、Provider 兼容切换与统一前端。

这样现有 CSV / SQD / RPC / SQD Cloud 都能够继续复用，并真正形成一个可维护的“智能下载系统”。
